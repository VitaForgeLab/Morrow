# v3 PRD — 阶段三：Agent 化健康助手（愿景与开放问题）

> **定位：不是毕设必需项**，是求职加分项与长期 side project。
>
> 本文件刻意写得"不完整"——它的作用是**记录方向与开放问题**，避免现在把还没想清的东西写死。
>
> 上游：[阶段一](v1_prd.md) 提供问答骨架与生成任务机制；[阶段二](v2_prd.md) 提供知识库检索与引用能力。

---

## 1. 愿景

Morrow 从「超声检查知识问答」进化为「**普适的个人健康知识与行动助手**」：

> 它不只回答问题，还**记得你**、**在你需要时主动开口**。

命名 `Morrow`（明天）的含义就是这件事：帮助今天的你，为明天的自己做得更好。这也是为什么产品名不带 RAG、超声这类专业词——产品边界会变，名字不应该跟着变。

---

## 2. 能力清单（假设，待验证）

### 2.1 长期记忆（Long-Term Memory）

- `user_profile`：关注点、健康状况、偏好、表达习惯
- `records`：检查记录、习惯打卡、活动记录
- 核心待解问题不在"存什么"，而在：**什么时候写、写什么粒度、怎么取、怎么遗忘与更新**

### 2.2 Tools

- `search_knowledge()` —— 复用阶段二的检索能力
- `save_memory()` / `get_records()` —— 记忆读写
- `reminder()` / `cron()` —— 定时与提醒
- 待评估是否需要：网络搜索、计算、单位换算

### 2.3 主动交互

- 定时反馈（如每周健康小结）
- 异常提醒（连续熬夜、漏检提醒）
- 基于记录的趋势发现

### 2.4 规划

- 多步任务：如"帮我整理一份术前准备清单"

## 3. 开放问题（现在不回答）

| 问题 | 影响什么 |
| --- | --- |
| Agent 框架选型：LangChain / LangGraph / 自研 loop | 可控性与调试难度 vs 开发速度 |
| 记忆的存储与检索：结构化表 / 向量记忆 / 混合 | 检索效果 vs 可解释性 |
| 主动交互的触发机制：定时任务（Celery / APScheduler）vs 事件驱动 | 架构复杂度与部署形态 |
| 需求边界：什么该主动、什么构成打扰 | 产品成败的关键 |
| 隐私边界：健康数据的存储、最小化与脱敏 | 合规与用户信任 |
| 产品形态：Web / 移动端 / 小程序 | 前端工作量与优先级 |

> 这些问题的答案**应该在阶段一二过程中自然浮现**，而不是现在拍脑袋定。阶段一二的实践会告诉你哪些记忆真的有用、哪些主动交互真的不烦人。

## 4. 与一二阶段的衔接（现在就要预留的设计）

即使阶段一、二不实现任何 Agent 功能，下面这几处**现在就要留口子**，否则将来要大改：

1. **`conversation` 需要有来源标记**（用户发起 / 系统主动发起）——主动交互本质上就是"系统创建了一个会话"。
2. **`model_config` 要支持多模型并存**——tools 调用、标题生成、检索改写可能用不同模型（阶段一的表结构已经预留，见 v1 §4）。
3. **消息与记忆要可关联**——"这次回答基于哪些记忆"必须可追溯，否则出了问题无法解释，也不符合医疗场景的审慎要求。
4. **生成任务不要写成只能被 HTTP 触发**——阶段一的"生成任务 detach"（v1 §7.1）正是定时任务与主动推送的底座，设计时把它抽成独立函数而不是绑死在路由里。
5. **`knowledge_base` 概念从阶段二就抽出来**（v2 §4），便于阶段三挂载多个知识域，不再局限于超声。

---

## 5. 优先级

- 低于阶段一、阶段二。
- 低于面试八股与算法刷题。
- 只在阶段一二完成、且求职有明显富余时间时启动。

换句话说：**它是甜点，不是主菜。**如果时间和精力冲突，砍它。

---

## 6. 明确不做（在此阶段之前）

- **不输出医疗诊断或用药建议**（红线，任何阶段都不越界）
- 不对接硬件 / 穿戴设备
- 不做社区、内容分发等社交功能
- 不做付费与商业化
